# jc-release — Candidate Release Boundary

Production upgrade remains **NO-GO pending review and deployment**. This local candidate restores operator-initiated upload and upgrade for Backend/Frontend/Admin, with archive size/hash, exact component identity, agent authentication and pre-apply backup. Successful isolated Go tests do not authorize production rollout.

Job has a separate *local candidate* upload/upgrade path. The server stores the Job-only canonical declaration; the Agent requires configured `job_environment` and at least three distinct `job_trusted_keys` (Ed25519 public keys in hex), verifies two independent signatures on the artifact hash, environment, generation and immutable image ID, checks the isolated `job-runtime/config` layout and Job/Core signer separation, and compares the loaded Docker image identity before Job-only Compose recreation. The Agent derives the Job address from its isolated plaintext signer and compares it with signed readiness; the signed public Core operator must match the Job V2 config and differ from the Job address. Core key custody and on-chain `operator()` still require independent evidence: public-address comparison does not prove them. No Core private key is required or copied into Job configuration. Absent trust, configuration or runtime prerequisites, `job_runtime_admission_unavailable` rejects before mutation. These checks are not production authorization; no trusted production keys or production Job runtime have been installed.

Phase 2 adds a separately signed, short-lived Job readiness assertion bound to the actual application Agent, host SSH key, release/image/generation and six local receipt hashes. It still cannot create, inspect or approve the underlying production backup, schema, signer, chain/RPC or permission evidence. Missing/untrusted evidence fails before the download. For the full contract, production blockers and an **offline review-only** Server/Agent build (not the older disabled-boundary upgrader), see [`SECOND-PHASE-REVIEW.md`](SECOND-PHASE-REVIEW.md) and [`SECOND-PHASE-PREFLIGHT.md`](SECOND-PHASE-PREFLIGHT.md).

Before container mutation the Agent persists `job_pending` to its state. A crash or unverified rollback blocks subsequent Job upgrades until an operator investigates and explicitly reconciles the state and container. First deployment failure removes only a container bearing this attempt's label and verifies absence; later deployment uses an image backup and verifies restored health and image. The journal is not automatic crash recovery. TGBot/Lang remain unavailable. Manual rollback by arbitrary release ID is not offered: the older implementation ignored the selected target and used whichever local backup was newest. No Backend image is published to GHCR.

The Web UI exposes upload and upgrade for Backend, Frontend, Admin and Job (Job requires a signed declaration). Its service-log targets remain Frontend, Admin and agent. The `deploy.sh` legacy shell/CLI path is separately disabled. The Fair Launch static suite is not a production admission or publication approval. Job signer, chain/RPC, database migration, backup/rollback and permissions require independent production evidence and authorized release decision; Fair Launch financial materialization remains disabled.
