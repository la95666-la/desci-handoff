# V3 Safe API proposals (code path; not a production activation record)

- Core alone reads `SAFE_API_KEY` from its **runtime environment**. Keep it out of Git, Admin/Vite variables, browser requests, deployment artifacts and logs. An absent key disables proposal submission; it does not disable read-only admission. Rotate any key that has been posted in a conversation.
- Admin must have project execute permission to submit; read permission only previews. The V3 policy path additionally requires an unexpired two-admin approval and a still-matching, independently checked V3 chain snapshot. Token proposals target only the pinned V3 Proxy and require the actual Owner Safe. The original USDT/TESTCAT flow is preserved; an additional address-based project-token path supports later tokens with chain-observed decimals (1–18) and exact Safe receipt checks. An Admin address is never sufficient to mark a token allowed. The token gate continues using its approved commercial read RPC.
- Preview reads the live Safe nonce and gets the transaction hash from the Safe contract on BSC 56. The actual Safe owner reviews target, calldata, value zero, CALL, nonce and hash, then signs the **32-byte Safe hash using `personal_sign`** in their own connected BSC wallet. Core recovers the signer, verifies `isOwner`, maps the signature to Safe's eth-sign mode and recomputes the hash/nonce before sending. No relayer or server key signs.
- Core uses `Authorization: Bearer` only on server-to-Safe Transaction Service requests. It checks the original hash and bounded pending queue before POST and reads back the exact transaction after 201. Unknown, timeout, conflict or readback mismatch is **not** success: look up the original Safe hash in Safe before considering any retry. There is no blind retry, automatic confirmation, execution or chain-state promotion.
- Safe Transaction Service proposals are not chain receipts. Another owner must confirm, and execution/receipt checks remain separate. Token receipt requires the original on-chain transaction hash; policy execution uses its separate observation/eligibility gates. TESTCAT cannot be proposed before USDT is confirmed as allowed. If both tokens already read `allowed=true`, this page offers no new token proposal and still requires historic original receipts for audit.
- Verify Safe service endpoint behavior, signer wallet support, runtime secret injection and E2E Safe queue behavior in a controlled environment before deploying. This change does not upload, deploy, sign or execute anything by itself.
