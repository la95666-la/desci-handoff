# IDO V3 four-eyes admission — development status

The default-off `idoV3Approved.enabled` path replaces per-project offline Set/scan release manifests with a project-scoped, executed two-admin Set identity. It does **not** replace actual Owner/Policy Safe signatures, operator outbox signing, original-hash receipts, canonical event scanning or wallet proof checks.

Source paths:

- `pkg/core/admin/controller/project_content.go`, `pkg/core/admin/service/approval/v3_set_handler.go`, `pkg/core/service/project/v3_approved_set.go`: submit and approve the exact economic request, persist the immutable binding and create calldata commitment in one transaction. Missing mode/schema refuses the Set; a diagnostic preview alone is not admission.
- `cmd/core/main.go`: the approved-mode startup branch rejects partial configuration and a V2-borrowed client without demanding the retired project-scoped offline Set/scan signatures. The actual signer identity is checked separately from the approval; a Set never grants custody of its private key.
- `pkg/common/idov3whitelist/approved_set_{record,runtime}.go`, `approved_schema.go`: check the executed approval, distinct actors, canonical request digest, fixed V3 runtime and DB fences. Project-token admission still requires actual Owner Safe configuration on the fixed Proxy.
- `pkg/core/service/project/v3_approved_create_{preflight,execute}.go`, `pkg/common/chaintx/v3_approved_{prepare_once,creation_audit}.go`: simulate before reserving, sign once through the durable nonce fence, and recover only the original hash. A reverted create releases its slot only after confirmed receipt reconciliation.
- `pkg/job/job/chainevent/v3_approved_{job,multi_scan,creation_bridge,unsigned_cleanup}.go`: enumerate every binding on the fixed V3 Proxy each tick; check each project's approval and canonical creation, scan bounded ranges and revoke a failed project's projection. The Job carries no relayer key. `pkg/job/job/starter.go` rejects simultaneous old/new V3 sources.
- `pkg/common/idov3whitelist/approved_scan_health.go`: a full-scan generation switches to `checking` *before* opening RPC and becomes `healthy` only after every binding was visited. The scanner serializes the starting and finishing binding counts against the Set writer's runtime lock; a newly approved project invalidates the prior healthy generation. Policy status and wallet proof require a recent completed generation as well as their own canonical project/receipt/cursor checks; a timeout or missed tick fails closed.
- `pkg/core/service/project/v3_approved_policy_*.go` and `v3_policy_{preview,review,proof}.go`: bind the versioned policy review and independently executed Safe transaction to the same Set identity. The proof consumer checks the actual Safe execution, scanned policy journal, wallet/session, canonical cursor and latest chain state.
- `joincare-deploy-ido-v3/migrations/2026_10_24_ido_v3_approved_set_identity.sql`: **unapplied draft**. The evidence table, immutable constraints and scan-health table have been rehearsed on disposable, network-none MySQL 8.4 with the existing migrations: pending→executed approval transition, rollback without partial Set, a second newly approved project, immutable economics/TGE and scan-health generation/count fences. The isolated test does **not** establish a canonical BSC RPC, Safe owner transaction or end-to-end wallet success. Never apply only this migration or manually mark it applied.

The production environment has **not** been migrated or switched. `idoV3Approved.enabled` is default-off; with no installed schema or missing configuration the V3 Set/Create/policy/proof paths refuse work. Do not confuse a successful unit test, Safe proposal, artifact upload or preview with an on-chain project. Before any rollout, rehearse the *full cross-process* Set→create→original receipt→Job→policy Safe→proof→wallet path, verify Core/Job have the same deployment-pinned Safe code identities and commercial read RPC, test rollback/reorg and partial-scan behavior, then separately authorize migration and deployment. The historical single-project signed manifest code still exists for test/backward compatibility, but the new V3 public routes must not fall back to it. No relayer private-key manual transactions.

The unrestricted disposable MySQL candidate script is **not passing** with this candidate: its historical `TestV3CreationBridgeDisposableMySQLOriginalAttempt` still drives the retired offline-manifest policy preview and receives HTTP 409 `V3_POLICY_PREVIEW_UNAVAILABLE`. The schema-only target passes, but is not a substitute for a new approved-mode cross-component integration test. No artifact should be uploaded on the strength of that narrower result.
