# IDO V3 Set signature handoff (candidate; not production admission)

This describes the **offline** Set review format implemented by
`pkg/common/idov3whitelist/set_admission.go` and the corresponding Core
configuration read in `pkg/core/service/project/v3_set.go`. It does not appoint
an authority, create a key, approve an application, configure a Safe, or turn
on production. The separately signed scanner `AdmissionManifest` has a
different domain and must **not** use this signing procedure or key.

## Who does what

1. The applicant submits using their own authenticated, primary bound wallet,
   or an authorized Admin explicitly creates an audited proxy copy of a prior
   approved application (not a wallet signature). Admin reviews the new
   application; an approved application creates a **new**
   `Setup` project ID. The ID is generated by the application service, not
   chosen by an operator and not copied from V2.
2. The project owner and business reviewer confirm the new project's terms.
   Previous V2 TESTCAT values can be used as a **proposal**, but historical
   sale/TGE timestamps cannot be reused. The reviewer checks raw/display
   amounts, supply, token addresses/decimals and V3 config, fee receiver,
   expiry, BSC chain and governance/runtime code hashes against current facts.
3. An authorized independent Set signer reviews the exact **typed request**
   JSON and `SetManifest` (including the new project ID, request digest and
   expiry). The signer, not the Backend or Admin, controls the Ed25519 signing
   key in an offline or approved HSM environment. No key material is sent to
   the agent, Admin UI, repo, chat, or jc-release. The signer's appointment,
   custody, rotation, revocation and separate review must be approved before
   any production use; a development test key is never production authority.
4. A release operator checks the detached signature **offline**, pins the
   approved public key, manifest and base64 signature under `idoV3Set` in
   protected Core configuration, then independently verifies the deployed
   configuration digest/identity. This is a distinct controlled release; a
   signature alone cannot enable V3. Do not place these values in an Admin
   request or an unverified database row.
5. The read-only V3 diagnostic preview does not consume this manifest (see
   `IDO-V3-SET-DIAGNOSTIC-PREVIEW.md`). On Set approval submission and again
   inside the separate four-eyes Set application, Core verifies the exact
   request digest, domain-separated signature,
   expiration, new `Setup` project, unverified V3 runtime and current chain
   facts. A changed field requires a **new** review and signature. Creation,
   scanner admission, wallet proof and financing have additional gates.

## Local deterministic review tool

From the Backend repository root, build from the reviewed source revision:

```sh
GOEXPERIMENT=jsonv2 go build -o /private/review/ido-v3-set-review ./cmd/ido-v3-set-review
```

Prepare `request.json` with the exact `OnchainParamsRequest` fields, including
`"contract_version":"ido_v3_stablecoin"`, and `manifest.json` with the exact
`SetManifest` fields from the source. The `request_digest` is
`0x` + SHA-256 of Go's `encoding/json.Marshal` of the typed request, **not** a
hash of the raw file. The helper rejects a mismatched digest and mismatched
project/token/owner. To emit the exact bytes covered by the Set signature:

This Set manifest no longer contains project/payment token code hashes. Both
token addresses and decimals/config getters remain checked against the V3
Proxy at a confirmed block; Proxy, Implementation, Owner Safe and Policy Safe
code identities remain pinned. Do not reuse an old signed manifest with a
different schema or assume that removing token hashes enables Set by itself.

```sh
/private/review/ido-v3-set-review --manifest /private/review/manifest.json \
  --request /private/review/request.json --preimage /private/review/preimage.bin
```

The output is `"joincare:ido-v3:set:v1\x00" ||
json.Marshal(typed SetManifest)` with **no trailing newline**. The tool prints
only the project ID and preimage hash and refuses to overwrite an existing
preimage. The signer must independently inspect the request and manifest,
agree on their hashes and sign these exact bytes using an approved Ed25519
offline device/process. The tool intentionally has **no key generation or
signing mode**. Convert the detached signature to a single-line standard
base64 file using the approved signer workflow. An independent reviewer checks
the externally supplied base64 public-key and signature files:

```sh
/private/review/ido-v3-set-review --manifest /private/review/manifest.json \
  --request /private/review/request.json \
  --public-key /private/review/public-key.b64 \
  --signature /private/review/signature.b64
```

Verification uses the same `VerifySignedSetManifest` as Core and rejects an
expired manifest, changed digest, foreign identity or bad signature. Save
only nonsecret hashes, identity, approval evidence and the verification result
to the protected release record. **Do not enable** `idoV3Set.enabled` simply
because this tool succeeds: the production runtime, independent Safe token
configuration, exact project, scanner/admission and rollback gates remain
separately required. USDT/TESTCAT being used by V2 does not change their
`allowed=false` values in the independent V3 Proxy.
